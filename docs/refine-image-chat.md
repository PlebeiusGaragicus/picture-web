# Refine Image In Chat

> **Deprecated.** This document is outdated and no longer maintained. See [`AGENTS.md`](../AGENTS.md) and the application source for current behavior.

## Goal

Add a true Gemini chat refinement mode for images. Instead of treating every edit as a stateless generation request, the user can open a chat on an existing image and iteratively ask for changes like:

- "make the jacket darker"
- "keep the face, but change the background to a studio"
- "try that again, but more cinematic"

Gemini's image generation documentation recommends chat / multi-turn conversation for iterative image editing. This feature should therefore model the interaction as a durable Gemini chat session, not as a series of unrelated image generation calls.

## Resolved Requirements

- Chat sessions must be resumable across application restarts.
- Chat sessions must retain the full chat history. Do not trim, compact, summarize, or rewrite old turns.
- The app needs a dedicated chat UI for image refinement.
- The chat UI may expose model settings that Gemini supports changing per turn.
- Thought signatures must be preserved in chat-session storage. They may still be stripped from ordinary asset provider metadata.
- Children generated by a chat must be visually grouped with the parent/chat branch so the canvas stays compact.
- Reference images may be added during a chat as new turn attachments.
- Prior reference images must not be deleted from persisted chat history. If the user wants to remove old references from model context, start or fork a new chat.
- Chat sessions, chat-generated assets, and assets referenced by chat history are archive-only in the app. The UI should not offer destructive deletion for them.

## Why Thought Signatures Matter

Google documents `thought_signature` as an encrypted representation of Gemini's internal reasoning state. The API uses it to preserve reasoning continuity across multi-turn and multi-step conversations.

The Gemini image generation docs also say:

- Chat / multi-turn conversation is the recommended way to iterate on images.
- Gemini 3 image responses can contain `thought_signature` fields on model parts.
- If a response part includes a thought signature, later requests should pass that part back exactly as received.
- The official Google Gen AI SDKs handle this automatically when using standard chat history features or appending the full model response object directly to history.
- Manual history reconstruction must not merge, remove, or rewrite signed parts.

This is especially important for a local app that needs to resume after restart. An in-memory SDK chat object is not enough by itself; the app must persist the complete provider conversation state needed to reconstruct or resume the chat.

References:

- [Google AI for Developers: Image generation](https://ai.google.dev/gemini-api/docs/image-generation)
- [Google AI for Developers: Thought Signatures](https://ai.google.dev/gemini-api/docs/thought-signatures)
- [Google Cloud: Thought signatures](https://docs.cloud.google.com/vertex-ai/generative-ai/docs/thought-signatures)

## Product Shape

From an image group, add a "Refine in chat" action scoped to the active asset. This opens a chat panel for that asset.

The first turn sends the source image plus the user's edit instruction to Gemini. Later turns use the same session history, including exact model response parts with thought signatures, so Gemini sees the edit chain as one conversation.

When Gemini returns one or more final image parts:

- Save each final image as a normal generated asset.
- Record the producing chat session and turn on the asset metadata.
- Add the generated image to a compact chat branch near the source image.
- Keep the chat panel open for follow-up refinements.

The UI should show user-visible messages and generated images by default. Debug/provider metadata should be hidden behind an explicit inspector affordance.

## Chat Settings

A chat session starts with the active asset's generation settings where possible:

- `model`
- `aspectRatio`
- `imageSize`
- `seed`, only if still meaningful for the selected model/API path

The chat UI may allow per-turn changes when supported by Gemini docs. Current documented examples show changing image config such as aspect ratio and resolution on a later chat turn.

Suggested controls:

- Model: default to the source asset model. Treat switching models mid-chat as advanced until tested.
- Aspect ratio: editable per turn when the selected model supports it.
- Image size: editable per turn when the selected model supports it.
- Thinking level: expose only for models where the docs document support, such as Gemini 3.1 Flash Image.
- Include thoughts: off by default; optionally enable for debugging/inspection.

Each turn should persist the effective settings used for that turn.

## Reference Images

Gemini allows messages to include text plus image parts, and the image docs show conversational image editing where later turns can include image bytes and a refinement instruction. Gemini 3 image models support up to 14 reference images in a workflow, with model-specific high-fidelity limits for objects and characters.

Product rules:

- Adding a reference image during a chat is allowed. It creates a new user turn with that image attached.
- Removing a reference from the compose box is allowed before sending the turn.
- Not reattaching a reference on a later turn is allowed.
- Deleting or rewriting a reference image from a previous persisted turn is not allowed, because it mutates chat history and can break thought-signature continuity.
- To intentionally drop old references from model context, the user should start or fork a new chat from the current generated image.
- Any asset used as a source or reference in a chat becomes protected from destructive deletion. Archiving can hide it from the active canvas/list, but the underlying `{id}.json` and `{id}.png` must remain available for chat replay.

## Data Model Direction

Keep asset metadata compact. Permanent asset JSON can continue stripping large opaque payloads such as `thought_signature` and inline image data. Those fields are not useful in immutable asset receipts and can be very large.

Store full thought-signature-bearing provider state only in a separate chat-session record, for example:

```text
photo-library/projects/<project>/chat-sessions/<session_id>/
  session.json
  blobs/
    <blob_id>.png
    <blob_id>.webp
```

Use a directory per chat session rather than one large JSON file. This keeps `session.json` reviewable while allowing provider image parts to live as local blob files. It also makes archive/backup behavior simple because the whole session is one folder.

## Canvas Behavior

Chat-generated images should be grouped with the parent/chat branch to use canvas space efficiently.

### Vocabulary

- **Candidate:** one image returned by a single Gemini request or chat turn.
- **Variant:** a candidate displayed inside the same image group as other candidates from the same generation intent. The current left/right image stack controls navigate variants.
- **Sibling:** a separate image group with the same parent refs but a different prompt, reference set, or generation intent.
- **Refinement:** a child image generated through a chat turn.
- **Chat branch:** the ordered set of refinements produced by one chat session.
- **Fork:** a new chat branch started from an existing source image or chat turn output, usually to intentionally drop old context/references or try a different model.

Batch outputs from the same request should be treated as candidates/variants, not siblings. For example, a normal generate request with `batchCount: 2` creates one image group with two variants. A chat turn that returns two final image candidates also creates one turn output group with two variants.

### Canvas Axes

Treat the canvas axes as orthogonal concepts:

```text
horizontal: alternate prompts, reference sets, and branches
vertical: chat refinement timeline
stack depth: variants/candidates from one request or turn
```

Example:

```text
Parent Image
  |- Draft prompt A -> [candidate 1 <-> candidate 2]
  |- Draft prompt B -> [candidate 1]
  `- Chat session
       v turn 1 refinement -> [candidate 1 <-> candidate 2]
       v turn 2 refinement -> [candidate 1]
       v turn 3 refinement -> [candidate 1 <-> candidate 2]
```

This means chat-generated assets are still parent/child lineage, but with a provenance subtype:

- **Generation child:** created from selected reference images plus a prompt.
- **Chat refinement:** created from a chat session, turn history, and the current/source image.

The underlying lineage can still use `generation.refs`, but the UI should draw or label chat refinement edges differently so the user understands that the child came from conversational state, not only a fresh reference-image prompt.

Two viable UI representations:

1. **Session rail beside the parent.** The source image group shows a small "chat" branch control. Opening it reveals a vertical rail of turn cards beside the parent. Each card displays the generated image group for that assistant turn, with variants stacked inside the card. This is probably the clearest first implementation because it maps directly to chat order and keeps the main graph compact.
2. **Collapsible chat container node.** A chat session appears as one larger canvas container connected to the source image. Inside it, generated turn outputs are shown as compact thumbnails or mini-stacks. Collapsing the container leaves one node labeled with the session title and latest output. This is more spatially efficient for long chats, but requires a richer canvas node type.

Recommended v1: implement the session rail. It uses the existing image group concept for turn outputs and can evolve into a collapsible container later.

Do not add generic up/down buttons directly to every image stack in v1. Up/down controls on an image could ambiguously mean parent/child navigation, chat turns, or other branch choices. Instead, expose a clear "Refinements" affordance on image groups with chat output. Opening that affordance reveals the vertical chat rail. Inside each rail turn card, keep left/right controls for variants from that turn.

Shared behavior:

- The source image group shows that one or more chat sessions branch from it.
- Each chat session owns a compact branch near the source.
- Each successful assistant image turn creates a child image group in that branch.
- If a single chat turn returns multiple final image candidates, those candidates are variants within that turn's image group.
- Chat-generated children still preserve normal lineage with `generation.refs`; `chatSessionId` and `chatTurnId` provide the chat provenance.
- Archived chat sessions and archived chat-generated assets remain on disk but are hidden by default, with a project-level "show archived" affordance.

Reason: a chat refinement changes the instruction history, not just generation parameters. It should not become a variant of the original image. But it also should not scatter unrelated sibling nodes across the canvas when all outputs belong to one refinement conversation.

## Archive And Deletion Rules

Chat history is part of the provenance chain and may contain provider state required by Gemini. For chat-linked data, the app should prefer archiving over deletion.

Rules:

- A chat session can be archived, not deleted, from the app UI.
- A chat-generated asset can be archived, not deleted, from the app UI.
- A source/reference asset used by any active or archived chat cannot be destructively deleted from the app UI.
- Archive hides the item from default canvas/list views but preserves all files needed for chat replay.
- API delete endpoints should reject protected assets with a clear conflict response once chat sessions exist.
- If a user really wants to purge data, that should be a separate future "danger zone" workflow with explicit warnings and dependency display, not the default delete action.

## Implementation Notes

Use the Google Gen AI SDK chat/history features where possible, because the docs state thought signatures are handled automatically when using standard chat history features or appending the full model response to history.

Do not rebuild the chat history from stripped asset receipts. The stripped provider metadata is intentionally not sufficient for resuming a thought-signature-aware Gemini chat.

For restart-safe resumability, persist enough provider state to recreate the SDK chat history or manually send the full `contents` history. The persisted representation must keep signed model parts exactly as returned by Gemini.

Large inline image data should not be duplicated in ordinary asset receipts. In chat-session state, store provider image bytes in local blob files and keep `data_ref` pointers in `session.json`. When resuming, load the blob bytes and reconstruct the Gemini parts with the same role, part order, MIME type, and `thought_signature` values.

Do not deduplicate, recompress, or transform provider blobs as part of chat persistence. The simplest maintainable rule is: save exactly the bytes needed to reconstruct the next Gemini request, and separately save normal generated asset PNGs for the app's image library.

Forking should be available but not central. The first-class path is continuing the same chat. A "Start new chat from this image" or "Fork from this turn" action is useful when the user wants to intentionally drop old references/context or try a different model without mutating the original session.
